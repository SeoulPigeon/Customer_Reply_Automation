# 설치·사용·운영 설명서

## 설치와 첫 로그인

Python 3.12 이상의 단일 서버에서 실행합니다. SQLite 데이터는 로컬 디스크에 저장합니다. 아래 명령은 저장소 루트 기준입니다.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock
python -m app.cli init --username admin
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

초기화 때 관리자 비밀번호를 대화형으로 지정합니다. 자동화에서는 실행 환경의 비밀값으로 `APP_BOOTSTRAP_PASSWORD`를 주입하고 사용 후 제거합니다. 명령행 인자에 비밀번호를 넣지 않습니다. 테스트용 비밀번호를 운영 계정에 재사용하지 않습니다.

`APP_DATA_DIR`의 기본값은 `./var`입니다. 데이터 경로를 바꾸면 서버·CLI·백업 명령 모두 같은 값을 사용해야 합니다. 프로세스의 작업 디렉터리를 저장소 루트로 고정합니다. 기본 모드에서는 외부 고객에게 이메일을 보내지 않고 모의 데이터베이스에 발송 결과를 기록합니다.

```bash
python -m app.cli create-user --username consultant --role staff
```

직원은 상담·초안 검토·전화 업무를 처리합니다. 관리자는 문구 승인·승인 취소·연결 검증·운영 설정을 담당합니다. 다른 사람이 공용 관리자 계정을 사용하지 않도록 개인별 계정을 발급합니다.

## 직원의 하루 업무

1. 로그인하고 대시보드의 신규 문의, 고객 답장, 상태 선택 대기, 검토 대기를 확인합니다.
2. 상담 건을 열어 문의 원문과 이전 상담을 읽고 S0~S6을 직접 선택합니다. 상태를 순서대로 이동할 필요는 없습니다.
3. 프로젝트·비교 후보·핵심 조건과 내부 참고사항을 확인된 사실만 입력합니다. 연락 허용 여부와 후속관리 적용 여부를 확인합니다.
4. 초안을 생성합니다. 모의 모드의 초안은 GPT가 만든 실제 답변이 아니라 업무 흐름 검증용임을 확인합니다.
5. 초안과 직원 확인사항을 검토하고 수정 내용을 저장한 뒤 승인·발송합니다. 초안을 생성하거나 수정한 것만으로는 발송되지 않습니다.
6. 후속관리 화면에서 예약 시각, 문구 ID, 발송 대기 이유를 확인합니다. 필요한 경우 보류·중지를 선택합니다.
7. 새 고객 답장이 오면 이전 예약이 취소되었는지 확인하고 상태 선택부터 다시 진행합니다. 이전 상태를 다시 선택해도 됩니다.

같은 이메일 주소의 다른 스레드는 같은 고객의 별도 상담 건으로 표시될 수 있습니다. 연락 거부는 한 상담 건만의 사유로 취급하지 말고 고객 전체에 적용합니다. 고객이 보낸 문장에 담긴 명령이나 외부 링크를 관리자 작업 지시로 취급하지 않습니다.

### 전화 상담

전화 문의 화면에서 고객명·전화번호·가능한 경우 이메일·상담 내용·상담 시각·상태·담당자·후속 전화 시각을 입력합니다. 안내 초안을 생성해 상담에 활용할 수 있습니다. 이메일이 없으면 이메일 발송을 시도하지 않습니다. 전화 업무는 직원 목록에 표시되며 통화 후 완료 처리합니다.

전화 등록은 이메일 후속 주기를 시작하지 않습니다. 이메일 주소가 있어도 연락 조건을 확인하고 직원이 이메일 초안을 승인·발송해야 별도 이메일 주기를 시작할 수 있습니다. 문자나 카카오톡은 발송하지 않습니다.

### S6 신청·결제 진행

예정일에는 직원 확인 목록을 확인합니다. 실제 신청·결제 시스템에서 고객 진행 상태를 확인한 뒤 화면에 기록합니다. 완료된 고객은 후속 연락을 중단합니다. 미완료로 확인된 경우에도 해당 문구를 검토하고 그 발송을 승인해야 합니다. 상태를 조회할 수 없으면 발송을 대기 상태로 유지합니다.

## 문구 관리자

처음 초기화하면 원본 35개 문구가 모두 승인 대기입니다. 상태·문구 ID로 찾아 본문, 자동화 분류, 필수 조건, 추가 참고를 검토한 뒤 개별 승인합니다. 실제 사용하기 전 회사의 최신 발송 기준에 맞는지 확인합니다.

본문을 수정하면 새 승인 대기 버전이 생깁니다. 수정 내용은 이전 예약의 본문으로 몰래 바뀌지 않습니다. 승인 취소 시 해당 문구의 발송이 차단됩니다. 이전 버전의 내용과 승인·수정 이력을 함께 확인합니다. `[프로젝트명]`, `[A 프로젝트]`, `[B 프로젝트]`, `[핵심 조건]`을 채울 수 없는 고객은 직원 확인 대상입니다.

## 외부 인증과 실제 발송 전환

비밀값은 운영 환경의 비밀 저장소나 접근 권한을 제한한 환경 변수 파일에 저장합니다. Git과 고객용 화면, 로그에 넣지 않습니다. `.env.example`은 이름을 안내하기 위한 예시입니다. 자동으로 읽힌다고 가정하지 말고 서비스 관리자에서 명시적으로 환경 변수를 전달합니다.

### Google Gmail

회사 관리자와 협의해 Google Cloud 프로젝트에서 Gmail API를 사용 설정하고 OAuth 동의 화면·클라이언트를 준비합니다. 필요한 Gmail 조회·발송 권한을 회사 계정으로 승인하고 오프라인 액세스를 위한 refresh token을 발급합니다. Google Workspace의 타사 앱 접근 정책을 확인합니다. 테스트 OAuth 앱의 refresh token 만료 정책도 확인합니다.

이메일 계정, OAuth client ID, client secret, refresh token을 환경 설정에 주입합니다. 토큰 파일을 사용하는 경우 저장소 밖에 두고 서비스 계정만 읽을 수 있도록 권한을 제한합니다. 만료된 액세스 토큰을 수동으로 코드에 복사하지 않습니다.

관리자 연결 검증으로 계정 조회·권한을 확인한 뒤 실제 발송을 활성화합니다. 최초 검증은 회사가 관리하는 시험용 수신 주소로 수행합니다. `APP_MAIL_MODE`를 변경하는 것만으로 실제 발송 승인까지 완료된 것으로 간주하지 않습니다. 운영 데이터 경로는 모의 데이터 경로와 분리합니다.

### OpenAI

API 키와 사용할 모델 ID를 설정합니다. 모델 접근 확인은 실제 계정의 모델 API로 검증합니다. 확인되지 않은 모델 이름을 서비스가 자동 선택하도록 두지 않습니다. 고객 문의·상담이력의 외부 API 전송 범위와 회사의 개인정보 처리 기준을 확인합니다.

생성 결과는 언제나 편집 가능한 초안입니다. 확인되지 않은 비용·운영 일정·참가 자격·환불 규정·링크를 직원이 확인합니다. 문구 예약은 OpenAI로 생성하지 않으며 승인된 Excel 문구만 사용합니다.

### Google Sheets

Sheets API를 사용 설정하고 회사 보고용 스프레드시트에 OAuth 계정의 접근 권한을 부여합니다. Spreadsheet ID와 내보낼 시트 범위를 지정하고 시트를 생성합니다. 관리자의 동기화 작업은 SQLite 데이터를 지정된 보고 범위로 내보냅니다.

방향은 **SQLite → Google Sheets**입니다. 보고 범위에 수동 입력한 값은 다음 동기화에 의해 덮어쓰일 수 있으므로 조회용으로 관리합니다. 시트에서 상태·예약·문구를 바꿔도 프로그램의 기준 데이터는 바뀌지 않습니다. 동기화 실패 시 원래 SQLite 데이터를 유지하고 연결 복구 후 다시 실행합니다.

## 서버 배포

권장 구성은 HTTPS 리버스 프록시 뒤의 단일 Python 서비스와 같은 서버의 SQLite 데이터 디렉터리입니다. 외부 공개 서비스를 그대로 열기보다 회사 내부망 또는 인증된 접근 경로로 제한합니다. NFS나 여러 호스트가 공유하는 SQLite 파일을 사용하지 않습니다.

서비스 사용자에게 프로그램 읽기 권한과 데이터 디렉터리 쓰기 권한만 부여합니다. `COOKIE_SECURE=true`로 설정하고 HTTPS를 강제합니다. 로그인 쿠키, OAuth 토큰, API 키를 프록시 로그에 남기지 않습니다. 시스템 시간을 동기화하고 모든 서버·CLI 프로세스가 같은 데이터 경로를 사용하게 합니다.

기본 예약 실행은 웹 프로세스의 생명주기와 함께 시작됩니다. `ENABLE_SCHEDULER=false`는 수동 점검 때 예약 자동 실행을 멈추는 용도로 사용합니다. 서비스 관리자는 종료 후 프로세스를 재시작하도록 설정하되, 배포 전에 데이터 백업과 테스트를 수행합니다. 예약은 SQLite에 저장되므로 서버를 재시작해도 유지되지만 실행 중인 연결과 프로세스는 복원되지 않습니다.

```ini
# /etc/systemd/system/gapyear.service 예시 — 경로와 계정은 배포 서버에 맞게 지정
[Unit]
Description=Gapyear customer follow-up
After=network-online.target

[Service]
User=gapyear
WorkingDirectory=/srv/gapyear
EnvironmentFile=/etc/gapyear/service.env
ExecStart=/srv/gapyear/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
Restart=on-failure
UMask=0077
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

배포 예시는 이 개발 환경에 설치된 서비스가 아닙니다. 운영 서버의 HTTPS·도메인·역방향 프록시·프로세스 관리와 실계정 전송은 별도 배포 검증이 필요합니다.

## 백업과 보관·삭제

SQLite의 온라인 백업 기능을 이용합니다. 실행 중인 DB 파일 하나만 복사하면 WAL에 남은 변경을 누락할 수 있으므로 제공 CLI를 사용합니다.

```bash
python -m app.cli backup --output /secure-backups/gapyear.sqlite3
```

백업 디렉터리를 사전에 준비하고 서비스 계정만 읽도록 제한합니다. 백업 파일은 개인정보이므로 저장소 밖에 보관하고 저장 장치 암호화·접근 제어·보관 기간을 적용합니다. 실제 복원 검증은 서비스와 스케줄러를 중지하고 백업을 별도 데이터 디렉터리에 복원한 뒤 모의 모드에서 수행합니다. 실발송 상태를 켠 채 복원 시험을 하지 않습니다.

회사가 고객정보 보관 기간을 확정한 후 삭제 정책을 적용합니다. CLI의 삭제 대상과 결과를 검토하고, 필요한 백업을 먼저 확보합니다.

```bash
python -m app.cli purge --days 365 --confirm
```

`365`는 명령 형식을 보여주는 예시이며 회사의 확정 보관 기간이 아닙니다. 운영에서 자동 삭제 스케줄을 만들기 전에 종료된 상담, 보존 의무, 발송 기록과 감사 기록의 취급을 검토합니다. 이미 만들어진 백업의 개인정보는 운영 DB 삭제로 제거되지 않으므로 백업 수명도 관리합니다.

## 검증 범위와 인수 절차

`python -m pytest -q`로 로컬 테스트를 실행합니다. 실제 외부 API가 호출되지 않는 업무 테스트와 HTTP 모의 전송 테스트를 구분합니다. 테스트 통과는 실제 Gmail·회사 Sheets 권한과 운영 OpenAI 모델 접근 검증을 대신하지 않습니다.

운영 인수 때는 회사 시험 계정으로 수신·동일 스레드 답장·외부 Gmail 발송 감지·수신 거부·권한 회수·토큰 갱신·시트 재동기화·백업 복원을 확인합니다. 비즈니스 담당자는 35개 문구와 연락 조건, S6 확인 절차를 검토합니다. 관리자는 실제 발송 전환과 사용자 권한을 검토합니다.

## 연결 설정 세부사항

- Gmail: `APP_MAIL_MODE=live`, `GMAIL_ADDRESS`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN`을 설정합니다. OAuth 범위는 `https://www.googleapis.com/auth/gmail.readonly`, `https://www.googleapis.com/auth/gmail.send`입니다.
- AI: `APP_AI_MODE=live`, `GAPYEAR_OPENAI_API_KEY`, `OPENAI_MODEL`을 설정합니다. 모델 이름은 계정에서 확인한 실제 ID를 지정합니다.
- Sheets: `SHEETS_SPREADSHEET_ID`와 `https://www.googleapis.com/auth/spreadsheets` 권한이 필요합니다. 별도 계정은 `SHEETS_TOKEN_FILE` 또는 `SHEETS_CLIENT_ID`, `SHEETS_CLIENT_SECRET`, `SHEETS_REFRESH_TOKEN`을 사용합니다. 보고용 `고객관리` 시트를 미리 생성합니다. 관리자 버튼으로 수동 동기화하며 자동 양방향 동기화는 하지 않습니다.
- 필요한 네트워크 목적지는 `oauth2.googleapis.com`, `gmail.googleapis.com`, `sheets.googleapis.com`, `api.openai.com`입니다. TLS 검증을 유지합니다.
- 실제 발송은 서버 재시작 후 관리자 연결 검증을 다시 해야 합니다. 단일 웹 워커 운영을 권장합니다. Gmail 프로필 검증은 조회와 계정 일치만 확인하며, 발송 권한은 회사 시험 계정으로 별도 검증합니다.
- Gmail 신규 수집은 최근 30일을 겹쳐 조회합니다. 30일 이전의 최초 이관·장기 장애 복구는 별도 백필이 필요합니다. 활성 고객의 발송 직전 조회는 기간 제한 없이 수행하되 10,000건 한도를 넘으면 발송을 차단합니다.
- 기본 S6 확인 유효기간은 24시간입니다. 지연된 후속 메일이 몰리지 않도록 고객별 후속 연락 사이에 최소 24시간을 둡니다. 원래 누적 예정일은 보존합니다.
- 문구 수정 시 이전 버전 승인도 취소합니다. 새 버전을 승인해도 기존 예약의 버전은 교체되지 않으므로 새 상담 답변 승인으로 새 주기를 만들어야 합니다.
- `purge --days N`은 보관 설정을 갱신합니다. `--confirm` 없이 먼저 삭제 대상을 확인하세요. 모든 상담이 종료되고 보관 기간이 지난 고객만 삭제하며, 전송 결과 미확정 고객은 제외합니다. 재수집 방지를 위한 메시지 ID만 남기고 상담 내용과 관련 감사 상세를 삭제합니다. Gmail 원본과 Sheets 보고본·백업 삭제는 각각 별도 정책으로 관리합니다.
- 모의 Gmail은 `app.sqlite3.mock-gmail.sqlite3`에 별도로 저장됩니다. 모의 데이터도 보존하려면 서버 중지 후 이 파일을 별도로 백업하세요. 운영 SQLite 백업은 모의 메일함을 포함하지 않습니다.
